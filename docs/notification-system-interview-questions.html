Notification System Interview Questions

Outbox pattern, reliability design, retry logic, deadlocks, idempotency, and follow-up questions

1. What is the architecture of this notification system?

This system is a reliable asynchronous notification pipeline built using PostgreSQL, Redis + BullMQ, Express, and background workers.

  • Client sends a notification request.
  • API validates the payload.
  • Notification and Outbox are inserted in one transaction.
  • Transaction commits.
  • Outbox relay scans pending rows and enqueues jobs.
  • Worker consumes the queue and sends the actual notification.
  • Status is updated to SENT or FAILED.
Follow-up: Why is this architecture needed? Because the system must survive crashes, Redis outage, delayed workers, and failed sends without losing intent.

2. Why do we need the outbox pattern?

The outbox pattern solves the problem of two different systems with separate transactions: PostgreSQL and Redis. You cannot reliably do both in one atomic operation.

If you save a notification in DB and then crash before enqueueing to Redis, you lose the notification. The outbox stores the intent in the same database transaction, so a relay can publish it later.

Follow-up: What failure are we solving? The crash window between “DB write” and “queue job add.” Without outbox, the notification may exist in Postgres but never be enqueued.

3. Why do we need an Outbox table when we already have a Notification table?

The Notification table answers: “What happened?” The Outbox table answers: “What still needs to be published to the queue?”

  • Notification tracks business state.
  • Outbox tracks queue publication intent.
  • Notification may still be pending even if it is already queued.
Follow-up: Why not just scan Notification where status = PENDING? Because a notification can already be in Redis and still remain PENDING, causing duplicate jobs if you enqueue again.

4. Why are Notification and Outbox written in one DB transaction?

Because both are part of the same business event and must be all-or-nothing.

If one succeeds and the other fails, the system becomes inconsistent. Using one transaction guarantees consistency.

Follow-up: What happens if the transaction fails? It rolls back completely and the API should report a failure so the client can retry.

5. What if the server crashes after the DB commit but before queue.add runs?

This is the classic outbox case. The DB commit succeeds, so both Notification and Outbox are durable. The relay reads pending Outbox rows later and enqueues the job.

Follow-up: Why is this safe? Because the durable intent is stored in PostgreSQL, which acts as the system of record.

6. What if Redis is down when the relay tries to enqueue?

The relay should leave the Outbox row as PENDING and retry later. The database still records the original intent, so the job is not lost.

Follow-up: Should the API fail if Redis is down? Usually no, if the database commit succeeded. Accept the request and process asynchronously.

7. Why can’t we call queue.add inside the same DB transaction?

Because PostgreSQL and Redis are different systems with different commit semantics. A DB transaction cannot include Redis writes atomically.

Follow-up: Why not do direct queue.add after commit in the API? Because crashes or temporary Redis outages still create a gap; the relay is a safer, retryable bridge.

8. What is the problem of duplicate jobs?

Duplicate jobs appear when the same notification is enqueued multiple times because of retries, multiple relay passes, or worker reprocessing.

That can result in duplicate sends.

Follow-up: How do you solve it? Use a stable jobId and idempotent worker logic.

9. Why is jobId important?

jobId gives each message a stable identity in BullMQ. If the system tries to add the same job again, Redis rejects it instead of creating a duplicate.

Follow-up: What happens without jobId? Duplicate jobs are likely and users may receive the same notification twice.

10. What happens if queue.add succeeds but the Outbox update fails?

This is a distributed system race. Redis and Postgres are not in one transaction. The queue may have the job, but the database still says PENDING.

The fix is idempotent jobId plus retry semantics. The relay simply tries again later, but the duplicate is blocked by the same key.

Follow-up: Can you guarantee exactly-once across DB and Redis? Not practically. You aim for at-least-once delivery with idempotency.

11. How does the outbox relay avoid duplicates?

The relay selects pending rows, marks them PROCESSING, and then calls queue.add. If a job with same ID already exists, BullMQ throws “already exists,” which the code treats as success.

Follow-up: Why is it dangerous to mark every exception as success? Because if Redis is down, you would incorrectly mark the outbox as processed and hide a real failure.

12. Why is “already exists” treated as success?

Because the intended result has already happened: the queue already has the job. The system should not keep retrying endlessly for the same ID.

Follow-up: What if the error is not “already exists”? Then it is a real queue problem, and the row should remain PENDING for retry.

13. Why is FOR UPDATE SKIP LOCKED used in the relay?

It prevents multiple workers from locking and processing the same outbox rows concurrently.

Follow-up: What happens without it? Multiple workers may enqueue the same job row more than once.

14. What is a deadlock, and why is it relevant here?

A deadlock happens when two transactions lock rows in opposite order and wait on each other forever.

In this system, deadlocks can happen if multiple workers update related rows concurrently. The solution is to keep transactions short, process rows in a consistent order, and use skip-locked patterns.

Follow-up: If deadlock occurs, how do you recover? Retry the transaction or let BullMQ retry the message.

15. Why is setInterval risky in the relay?

setInterval triggers on a fixed clock, not after the previous task finishes. If one run is slow, the next run can overlap and process the same data again.

Follow-up: How do we solve it? Use an isRunning lock so only one relay run executes at a time.

16. Why is forEach with async callbacks dangerous?

forEach does not await async callbacks. It schedules them and moves on. This can cause race conditions and duplicate processing.

Follow-up: What is safer? Use for...of with await inside the loop.

17. Why do we need multiple statuses?

Statuses represent the lifecycle of a notification:

  • PENDING: created, not yet processed
  • PROCESSING: actively being handled
  • SENT: successfully delivered
  • FAILED: delivery failed and needs recovery
Follow-up: Why not use only a Boolean? Because the system needs more than “done or not done” — it needs lifecycle visibility.

18. Why does the worker check if notification.status === 'SENT'?

This is idempotency logic. If a message is retried or redelivered, the worker should not send it twice.

Follow-up: Why is idempotency essential? Because async systems may retry a message after partial success.

19. What is the issue with returning an object inside a Prisma transaction callback?

Returning a normal object from inside a transaction callback may look like success to Prisma and incorrectly commit, even when you intended to fail.

Follow-up: What is the correct pattern? Throw an error inside the transaction, so Prisma rolls back the whole transaction.

20. Why can validation middleware cause a request to hang?

If validation fails but the middleware does not send a response and does not call next(), the request remains open indefinitely.

Follow-up: What is the correct fix? Return a response immediately with status 400 and a clear error body.

21. Why does the system accept the request even if Redis is temporarily down?

Because the business intent is already durable in Postgres. Once the DB transaction commits, the request has been accepted.

Follow-up: When should the API fail? When validation fails or the DB transaction fails.

22. What if the queue is full or the worker cannot keep up?

This becomes a capacity and backpressure problem. BullMQ can still hold jobs in Redis, but the system must have retry policies, queue monitoring, and bounded retries.

Follow-up: What should you monitor? Queue depth, worker lag, retry counts, and failure rate.

23. What is DLQ and why do we need it?

DLQ stands for dead-letter queue. It is used for events that fail repeatedly and should not continue retrying forever.

Failed notifications can be marked with a pending DLQ state and recovered manually or automatically later.

Follow-up: Why not retry forever? Some failures are permanent or expensive to retry.

24. What is the difference between Outbox Relay and Worker?

Relay: DB to Redis. Worker: Redis to external delivery provider.

Follow-up: Why separate them? Because they fail in different places and should be independently retried and monitored.

25. What are the hardest failure modes in this system?

  • Crash between DB commit and Redis enqueue
  • Redis outage during publication
  • Duplicate job creation
  • Worker retry storm
  • Lock contention and deadlock
  • Partial success between queue and DB state
Follow-up: How are they handled? Through durable DB intent, idempotent jobs, retry loops, lock-aware DB queries, and explicit status tracking.

26. What is the most important interview takeaway?

The key design principle is to make the database the source of truth and the queue a transport layer. That makes the system resilient, retriable, and recoverable under partial failures.

27. How would you answer the full interview summary?

We designed the notification system as an asynchronous, durable, idempotent pipeline. The database is the system of record. We store Notification and Outbox in the same transaction so intent is never lost. The outbox relay publishes pending events to Redis/BullMQ, and a separate worker handles delivery with retries, idempotency, and dead-letter handling. The system aims for at-least-once delivery with idempotent processing rather than exact once across independent systems.

28. Quick cheat sheet

Failure What we do
DB down during accept Fail the request and retry later
Crash before commit Transaction rolls back
Crash after commit before queue publish Outbox row remains pending and relay retries
Redis down Leave Outbox pending and retry later
Duplicate job Use stable jobId and idempotent worker logic
Deadlock Short txns and consistent ordering / skip-locked
Permanent provider failure Retry with exponential backoff and DLQ
Final interview answer:
“We built the notification system as a durable async pipeline. The database is the source of truth, the outbox records the intent to enqueue, the relay publishes jobs to Redis, and the worker sends the actual notification with retries, idempotency, and dead-letter handling. The design is optimized for partial failures and recovery, not perfect atomicity across separate systems.”
